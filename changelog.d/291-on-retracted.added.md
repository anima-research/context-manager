- `ContextStrategy.onRetracted(rows, ctx, { undone, removed, ids })`: the strategy hears rows as they leave the agent's window (agent-framework #291), with the rows that left, in the order the window held them, every shard of a body, and a context whose view no longer holds them. `ids` names every row that left in the call, in the same order, and `rows` gives the ones the manager can give: a row the store holds, or one a removal through this manager read before it went. A row removed through another manager, which this one doesn't hear, has no row to give: it comes by its id alone, with `removed: true`, and `rows` can be empty, so a strategy that keeps rows by id lets go of it all the same.
  - `retractRows` calls it once per call, after the rows are out and before it returns, with `undone` as given and `removed: false`; the rows the store no longer holds, which it takes out by their ids, are told in a second call of their own, by `ids` alone, with `removed: true`. `retractRemoved` and `retractAbsentRows` call it by `ids` alone, with `removed: true`. Once a host presents rows on a branch, a removal through the manager (`removeMessage`, `removeMessages`) of rows the window held calls it with the rows as they were before they went, `removed: true`, whether or not the window's tombstone could be written, since the removal stands; a row whose tombstone failed is told again, by its id, when `retractAbsentRows` takes it out. A `presentRows` that puts a body back whole, its first shard out and later ones in, calls it for those later shards before `onPresented` hears the body. In legacy mode a removal calls nothing: the window is the record, and a strategy that folded the row keeps what it folded, as before.
  - Fire and forget, as `onPresented` (#288): a throw or a rejection is logged as `Strategy onRetracted failed for …`, naming the rows, and the rows stay out. On a chronicle without the batched append (see the window index entry), a tombstone write cut short tells the strategy the rows it took out before it. While the strategy initializes, the calls wait and are made in order once it has, before the rows presented meanwhile are heard; a row presented again since is still given, and a row the initialized branch holds at the ordinal it left, in its window and its record (a branch made before it left), or any row while that branch is in legacy mode, is left out.
  - `AutobiographicalStrategy` (and `KnowledgeStrategy`) let go of what covers a row that left, every row `ids` names: each L1 with the row among its sources is dropped, with every summary above it, and a summary the drop leaves without its parent renders and merges again; each chunk record holding the row gives it up and is compressed again over the rows it keeps (one left with none is removed). The summaries, chunk records and merge queue are written at once, with one `[autobiographical] … row(s) left the window` warning naming what changed. A compression or merge in flight over the row writes nothing when it lands. So an undone turn's rows no longer render folded after the undo, and a redo, which presents them again at the end of the window, renders each once, raw there until it is folded again, where it rendered twice before (raw, and inside the summary at its old place). A removal through one manager unfolds the row on every reader the host repairs with `retractRemoved` or `retractAbsentRows`, not only on the manager that removed it. The cost is the fold work over those rows, on each reader: the summaries above them are written again. In legacy mode nothing changes. `PassthroughStrategy` and `WindowedPassthroughStrategy` define no `onRetracted`.
  - A row that left and was presented again before the strategy heard it go (both while it initialized) is in the window again when it is told: what covered it at its old place goes all the same, and a chunk record made over it at its new place keeps it. Should the strategy never hear it go (the process stopped between the window's tombstone and the strategy's own writes), its open, once a host presents, demotes the summary the row's new place leaves non-contiguous instead of refusing the store with `StoreTopologyError`: the summary is dropped with every summary above it, an L1's chunk record is compressed again over its longest run of rows the window holds together, and its other rows are chunked again where the window holds them, with one `[autobiographical] the window holds the leaves of … apart` warning. This applies under `topologyPolicy` `'reject'`, the default; `'report'` and an audit-only open record the summary and change nothing, and a store in legacy mode is refused as before.
