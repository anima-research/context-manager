- **Hosts and packages that install context-manager:** it now depends on `@animalabs/chronicle` `^0.5.0` (was `^0.4.0`), the chronicle release that carries the identity-stamped batched append (`appendManyToStateJsonWithIdentity`), with which a window write is one record and one presentation point (see the window index entry), and the store views `derive()` reads. A `^0.4.0` range let an install take chronicle 0.4.x, on which a host that presents writes the window down one record per row, with no warning: about 23 seconds and 63 MB of log for a 200,000-row namespace, against a quarter of a second batched, on one synthetic store. The new range makes that gate mechanical: an install either gets the batched append or doesn't resolve.
  **Who needs to act:** a host or package that depends on chronicle itself, such as agent-framework and connectome-host, which take the matching range alongside this release so that npm installs one chronicle for both. Until chronicle 0.5.0 is published, an install of this release doesn't resolve, and the lock file, which still names 0.4.0, is regenerated once it is (`npm install`, then `npm ci` checks it).
  **Migration:** take `@animalabs/chronicle` `^0.5.0` alongside this release. A store chronicle 0.5 writes a batch to moves to `MANIFEST` version 2, which older chronicle releases refuse (see the window batches entry).
  **Unchanged:** context-manager's code, which detects the batched append at each write and keeps the one-record-per-row path for a store handle without it.
