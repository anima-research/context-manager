- Each manager has a window: the stored rows its agent was shown, in the order it was shown them (agent-framework #291). Every strategy read and every compile follows the window, while the store's record keeps the order rows arrived in, so agents that share a slot, or one that merges another's with `auxiliaryMessageViews`, can each be sent what their own requests carried. Until a host presents a row on a branch the manager is in legacy mode: its window is the merged record itself, read live, compiles are byte for byte what they were, and nothing new is written to the store.
  - `presentRows(ids)` presents rows: they enter the window after the rows already there, in the order given, and it returns each one's index ordinal. A body stored as shards goes whole, named by the id `addMessage` returned for it. It refuses, presenting nothing, an id no merged slot holds, a row already in the window, a row named twice and a later shard named without its first. The first call on a branch writes the window down as it stands (every row of the record, in record order), and from then on the window grows only by presentation. A host that presents starts each agent's window at boot, with `presentRows([])`.
  - `retractRows(ids, { undone? })` takes rows out. Each leaves a hole at its ordinal, so no other row's ordinal moves, and a row presented again takes a new ordinal at the end. With `undone`, they are an undone turn's rows, which `getUnpresentedMessages()` leaves out until a later `presentRows` names them.
  - Reads: `presentationMode()` (`'legacy'` or `'presented'`), `ordinalOf(id)`, `indexLength()`, `presentedLength()`, `getPresentedMessages()` (the window before the view filter, the same array while it is unchanged), `getUnpresentedMessages()` (rows that arrived and weren't presented, in record order) and `lastPresentedSequence()`. New exports: `windowIndexStateId(namespace)` and the `PresentationMode` type.
  - Once a host presents, the view filter applies to the window, `renderAsNewest` renders a row the window doesn't hold yet as null, and `noteRequestSent` vouches only for rows in the window: present the rows a request carried before noting them.
  - The window is a Chronicle append-log state, `<namespace>/presentation`, registered at the first presentation, so it is per branch, survives a restart and is carried by `fork()`. Each row presented is one record for now, and the first presentation writes one per stored row.
  - Not yet: `derive()` carries the window only for a strategy without a derivation manifest, under its namespace prefix (a derived manager under the autobiographical or windowed strategy starts in legacy mode), and `branchAt()` cuts at the row's own sequence rather than at the write that presented it.
- `MessageStoreView.positionOf(id)`, optional: a message's position in `getAll()`. Compile provenance finds a raw body by its position instead of its sequence, since a window needn't be in sequence order; a run of raw entries still costs one lookup and reads no stored message (#273).
