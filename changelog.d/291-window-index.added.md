- Each manager has a window: the stored rows its agent was shown, in the order it was shown them (agent-framework #291). Every strategy read and every compile follows the window, while the store's record keeps the order rows arrived in, so agents that share a slot, or one that merges another's with `auxiliaryMessageViews`, can each be sent what their own requests carried. Until a host's first `presentRows` (or a `retractRows` that names a row) writes the window down on a branch, the manager is in legacy mode: its window is the merged record itself, read live, compiles send byte for byte the messages they sent, and nothing new is written to the store. A compile's provenance does change: its rendered layout is `v: 3` (see the fold-journal entry).
  - `presentRows(ids)` presents rows: they enter the window after the rows already there, in the order given, and it returns each one's index ordinal. A body stored as shards goes whole, named by the id `addMessage` returned for it. It refuses, presenting nothing, an id no merged slot holds, a row already in the window, a row named twice and a later shard named without its first. An index that pre-release builds wrote one record per row, before batched writes (below), can hold a body's first shards in the window and the rest out, left by a call cut short partway through the body or by a branch or `derive()` cut between its shards' presentations; naming the body again, by its first shard's id or by the first shard the window lacks (which `getUnpresentedMessages()` lists with the rest), presents only the shards it lacks, at the end of the window, and the shards in it keep their ordinals. A row presented in between stays between the two runs, and compile provenance then reports neither complete. A body such an index holds the other way round, its first shard out and later ones in (a `retractRows` cut short after the first shard's tombstone), is put back whole: naming it by its first shard's id takes its later shards out and presents the body at the end, in body order, in the call's one write, and the strategy hears those shards leave (`onRetracted`), then the body enter. The first call on a branch writes the window down as it stands (every row of the record, in record order, then a header), in one record, and finishes a write-down such an index holds interrupted; from then on the window grows only by presentation. A host that presents starts each agent's window at boot, with `presentRows([])`. The header is written last and is what switches the mode, so a write-down such an index holds cut short, by a failed append or a crash, leaves the manager in legacy mode, its window still the whole record, and the next `presentRows`, or a `retractRows` that names a row, writes only the rows still missing, then the header (a call that writes nothing in legacy mode, such as `retractRows([])`, leaves it as it is).
  - `retractRows(ids, { undone? })` takes rows out. Each leaves a hole at its ordinal, so no other row's ordinal moves, and a row presented again takes a new ordinal at the end. With `undone`, they are an undone turn's rows, which `getUnpresentedMessages()` leaves out until a later `presentRows` names them. `retractRows([])` writes nothing, in either mode. Any other call in legacy mode is a mode switch: it writes the window down first, as `presentRows` does, so rows stored after it enter the window only when presented.
  - Reads: `windowMode()` (`'legacy'` or `'presented'`), `ordinalOf(id)`, `indexLength()`, `presentedLength()`, `getPresentedMessages()` (the window before the view filter, the same array while it is unchanged), `getUnpresentedMessages()` (rows that arrived and weren't presented, in record order, with the shards lacking from a body whose first shards are in the window, even an undone turn's) and `newestWindowSequence()` (the newest store sequence among the rows in the window: a row's own, not the write that presented it, so not where the window reached; for that, compare ordinals). New exports: `windowIndexStateId(namespace)` and the `WindowMode` type. The mode, the newest row and the state are named by the window, apart from `acceptRound`'s `presentation`, which says how a provider round carried a compile and has nothing to do with `presentRows`.
  - Once a host presents, the view filter applies to the window, `renderAsNewest` renders a row the window doesn't hold yet as null, and `noteRequestSent` vouches only for rows in the window: present the rows a request carried before noting them.
  - The window is a Chronicle append-log state, `<namespace>/window`, registered at the first presentation, so it is per branch and survives a restart. An index in a format this version doesn't read (a header naming another format, or items it can't read and no header) reads as the record, with a warning, and `presentRows` and `retractRows` refuse to write to it. So does a window state that holds no list of items, such as an object another writer set there, and one whose value the store can't give as JSON: the window is the record (legacy mode), one warning says what the state holds (`holds an object ({"someone":"else"}), not a list of index items`, `holds a value that isn't JSON (…)` or `holds records the store can't read back as one value (…)`), and `presentRows` and `retractRows` refuse to write to it with an error that says the same. A read of the state that fails any other way is thrown, and the next read tries again.
  - Each write to the window is one record, at one sequence, through chronicle's `appendManyToStateJsonWithIdentity` (the identity-stamped batched append of chronicle 0.6.0, which this release requires: a manager over a store handle without it is refused at open, `derive()` and `reopenDerived()` with `ContextManager: the store handle has no appendManyToStateJsonWithIdentity, …`, before any record changes; see the chronicle entry): the write-down, the rows of one `presentRows` call, and the tombstones of one `retractRows`, `retractRemoved` or `retractAbsentRows` call or of one removal. The store keeps or loses such a record whole, and a write it refuses has written nothing: a refused write-down leaves the manager in legacy mode, a refused `presentRows` enters no row and tells the strategy nothing, and a refused `retractRows` takes nothing out. After any throw the window index is read again from the store. A write of one row is one record, through the single form. Pre-release builds, before batched writes, wrote every row presented, and every row of the write-down, as a record of its own; an index they wrote reads as one written in batches, and context-manager writes none. The first batched record moves the store to chronicle's `MANIFEST` version 2 (see Breaking). A batch is one presentation point: a cut at any row it presented keeps the whole batch (see the `branchAt` entry). `bench/window/write-down-bench.mjs` measures the write-down in one record and in one record per row, as those builds wrote it, and checks the two leave the same window; in one run on one synthetic store of 50,000 rows on one machine (an Apple M5, under other load), the write-down took 69 ms in one record against 4.2 s in 50,001, the log grew by 1.9 MB against 15.3 MB, and a reopen that reads the window took 0.05 s longer than one before the write-down against 0.6 s longer. These are one store's numbers, not a guarantee for a resident store.
  - `presentRows`, `retractRows`, `retractRemoved` and `retractAbsentRows` throw `WindowWriteOutcomeUnknownError`, a new export from the root, when the store throws on the window index's write and the index then can't be read again to tell whether the write landed. Where it reads again, the write's own error is thrown, whether the store kept the write or refused it: `ordinalOf` or `windowStatusOf` tells which, the strategy has heard what a kept write did, and a retry of one is refused (in the window already, or not in it). The error carries the write's own error as its `cause`, the failed read's as `readError`, the call as `operation`, and the rows the write would have put in and taken out as `entering` and `leaving`; its message ends with the cause's message. The write is one record, so the store holds all of it or none of it, and `windowStatusOf` tells which once the index reads: a row that entered is refused by `presentRows` as in the window already, and a row that left by `retractRows` as not in it. For `retractRemoved` and `retractAbsentRows`, whose rows the store no longer holds, `windowStatusOf` reads `'absent'` either way: `ordinalOf` tells (undefined once a row is taken out), and calling either again takes out only what is still there. The strategy hears what the write did (`onPresented`, `onRetracted`) at the next write to the window on the branch it was made on, `presentRows([])` among them, before that call's own work, and hears nothing of a write the store didn't keep; where the store can't say which branch that was, nothing waits (below), and the error's message says so.
  - A branch starts with the window as it stood at its branch point: `fork()` and `branchAt()` carry it, and `derive()` lists it among the states the manager owns, whatever the strategy's derivation manifest names. A manager derived at the head starts with its parent's window and its arrived-and-not-presented rows, from the parent's reading of the window rather than a new read of the store. One derived from `atSequence` starts with the window as it stood then, which names only rows stored by then. `reopenDerived()` finds the window on the derived branch. A parent that hadn't written its window down by the branch point (its first `presentRows`, `presentRows([])` among them, or a `retractRows` that names a row) has no window written there, and the branch is in legacy mode, its window the record up to the cut: a cut at the sequence of a row stored before the write-down holds that row in the child's window.
  - A row removed with `removeMessage` or `removeMessages` leaves the window as `retractRows` takes a row out: a tombstone at its ordinal, so no other row's ordinal moves. In legacy mode nothing is written. A removal through another manager on the same slot isn't heard: a host takes that row out of each other window that holds it with `retractRemoved(ids)`, naming the rows the removal took, or with `retractAbsentRows()`, which finds every such row, at boot say (see the entry for them); each tells that manager's strategy, which lets go of what it folded of the row. `retractRows` takes a row the store no longer holds out by its id too, and also takes out a row the record still holds, which those two pass over. A tombstone that can't be written, or a window that can't be read before a range is removed, is logged, and the removal stands. Until one of those calls takes such a row out, it keeps its ordinal: the window's listing and the compile leave it out, but `ordinalOf` still gives its ordinal and a strategy's `StrategyContext.window.ordinals()` still maps it, so a host that keeps watermarks by ordinal takes it out of each window that holds it.
- `MessageStoreView.positionOf(id)`, optional: a message's position in `getAll()`. Compile provenance finds a raw body by its position instead of its sequence, since a window needn't be in sequence order; a run of raw entries still costs one lookup and reads no stored message (#273).
- A write to the window that first settles an earlier write whose outcome was unknown (`WindowWriteOutcomeUnknownError`) throws, writing nothing, when a strategy hook that hears what the earlier write did moves the store's branch: the call was given the record of the branch it was made on, and would have written that record down into the other branch's window, or taken out of that window every row the record lacks. Its error names both branches. The earlier write stays settled, and a call made again works on the branch the store is on.
- A window write whose outcome is unknown waits to be settled on the branch the store was on before the write, read then, so a store that can't say its branch once the write has thrown still settles it at the next write on that branch. Where the store can't say its branch before the write either, nothing waits: a warning says so, and so does the `WindowWriteOutcomeUnknownError`'s message, which says the strategy reads the window at its next select instead of that it hears at the next write.
- A write-down (the first `presentRows` or `retractRows` on a branch in legacy mode) that the store throws on, where the window index then can't be read again to tell whether it landed, throws `WindowWriteOutcomeUnknownError` too, with `entering` and `leaving` empty and a message that says whether the window was written down is unknown; `windowMode()` tells which once the index reads. A write-down puts no row in the window and takes none out, so nothing waits to be heard.
- A window state that holds JSON `null` reads as another version's index too, as one that holds an object or a string does (`holds null, not a list of index items`): the window is the record, with one warning, and `presentRows` and `retractRows` refuse to write to it. A state with no record at all is still no index, and the first presentation writes the window down.
- Finishing a write-down that an index of pre-release builds holds cut short, where a slot merged since (`auxiliaryMessageViews`) holds rows stored before the ones it wrote, takes those out and writes every row of the record again, in record order, in the call's one record, so the window is the record as legacy mode read it, not the rows written first and the older ones after them.
- A removal through the manager (`removeMessage`, `removeMessages`) whose telling of the strategy fails in the manager's own work (the context it builds) logs it, as before, and the call now waits, to be made at the strategy's next notification, with the rows as they were before they went.
- A removal the strategy's `onCompressionHoldsReleased` hook makes through the manager, while a removal's release of holds runs it, leaves the outer removal's rows to leave the window and be told as that removal read them. Before, the hook's removal cleared what the outer one had read: a range's rows kept their ordinals, untold, and a single row was told by its id alone.
- A `presentRows` whose write lands and whose read of the index after it, for the ordinals it returns, throws goes as a write that threw: the strategy hears the rows that entered before the read's error is thrown, where the index reads again, and otherwise the call throws `WindowWriteOutcomeUnknownError` and the strategy hears them at the next write on that branch. Before, the read's error was thrown with nothing told or waiting, and a retry was refused, the rows being in the window.
- Finishing a write-down that an index of pre-release builds holds cut short, where a row it wrote has since been removed in legacy mode, takes that row out without counting it among the rows that left the window (`WindowIndexView.left()`): it was never in a presented window, so a folding strategy keeps what folded it at its next open, as after any removal in legacy mode. Before, that open let go of the summaries over it.
- A removal through the manager whose settling of an earlier window write (one whose outcome was unknown) runs a strategy hook that takes the removed row out itself (`retractRows`) tells the strategy the row left once, by that hook's call. Before, the removal told it a second time, from the ordinals it read before the settlement.
- A removal through the manager whose strategy's `onCompressionHoldsReleased` hook, which the removal's release of holds runs, moves the store's branch (`switchBranch`) takes nothing out of the window of the branch the store is on then, whose record may still hold the rows, and tells no strategy; it warns, and on the branch the removal was made on the rows keep their ordinals until `retractAbsentRows` takes them out there. Before, it took them out of the other branch's window and told its strategy they were removed.
