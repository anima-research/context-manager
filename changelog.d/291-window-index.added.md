- Each manager has a window: the stored rows its agent was shown, in the order it was shown them (agent-framework #291). Every strategy read and every compile follows the window, while the store's record keeps the order rows arrived in, so agents that share a slot, or one that merges another's with `auxiliaryMessageViews`, can each be sent what their own requests carried. Until a host presents a row on a branch the manager is in legacy mode: its window is the merged record itself, read live, compiles send byte for byte the messages they sent, and nothing new is written to the store. A compile's provenance does change: its rendered layout is `v: 3` (see the fold-journal entry).
  - `presentRows(ids)` presents rows: they enter the window after the rows already there, in the order given, and it returns each one's index ordinal. A body stored as shards goes whole, named by the id `addMessage` returned for it. It refuses, presenting nothing, an id no merged slot holds, a row already in the window, a row named twice and a later shard named without its first. On a chronicle without the batched append (below), each row presented is one record, so a call cut short partway through a body, or a branch or `derive()` cut between its shards' presentations, can leave a body's first shards in the window and the rest out, there or in an index such a chronicle wrote; naming the body again, by its first shard's id or by the first shard the window lacks (which `getUnpresentedMessages()` lists with the rest), presents only the shards it lacks, at the end of the window, and the shards in it keep their ordinals. A row presented in between stays between the two runs, and compile provenance then reports neither complete. A body such a chronicle left the other way round, its first shard out and later ones in (a `retractRows` cut short after the first shard's tombstone), is put back whole: naming it by its first shard's id takes its later shards out and presents the body at the end, in body order, in the call's one write, and the strategy hears those shards leave (`onRetracted`), then the body enter. The first call on a branch writes the window down as it stands (every row of the record, in record order, then a header), and finishes an interrupted write-down; from then on the window grows only by presentation. A host that presents starts each agent's window at boot, with `presentRows([])`. The header is written last and is what switches the mode, so a write-down that a failed append or a crash cuts short, which only such a chronicle can do, leaves the manager in legacy mode, its window still the whole record, and the next call writes only the rows still missing, then the header.
  - `retractRows(ids, { undone? })` takes rows out. Each leaves a hole at its ordinal, so no other row's ordinal moves, and a row presented again takes a new ordinal at the end. With `undone`, they are an undone turn's rows, which `getUnpresentedMessages()` leaves out until a later `presentRows` names them. `retractRows([])` writes nothing, in either mode. Any other call in legacy mode is a mode switch: it writes the window down first, as `presentRows` does, so rows stored after it enter the window only when presented.
  - Reads: `windowMode()` (`'legacy'` or `'presented'`), `ordinalOf(id)`, `indexLength()`, `presentedLength()`, `getPresentedMessages()` (the window before the view filter, the same array while it is unchanged), `getUnpresentedMessages()` (rows that arrived and weren't presented, in record order, with the shards a body partly in the window lacks, even an undone turn's) and `newestWindowSequence()` (the newest store sequence among the rows in the window: a row's own, not the write that presented it, so not where the window reached; for that, compare ordinals). New exports: `windowIndexStateId(namespace)` and the `WindowMode` type. The mode, the newest row and the state are named by the window, apart from `acceptRound`'s `presentation`, which says how a provider round carried a compile and has nothing to do with `presentRows`.
  - Once a host presents, the view filter applies to the window, `renderAsNewest` renders a row the window doesn't hold yet as null, and `noteRequestSent` vouches only for rows in the window: present the rows a request carried before noting them.
  - The window is a Chronicle append-log state, `<namespace>/window`, registered at the first presentation, so it is per branch and survives a restart. An index in a format this version doesn't read (a header naming another format, or items it can't read and no header) reads as the record, with a warning, and `presentRows` and `retractRows` refuse to write to it.
  - Each write to the window is one record, at one sequence, where chronicle has `appendManyToStateJsonWithIdentity` (the identity-stamped batched append): the write-down, the rows of one `presentRows` call, and the tombstones of one `retractRows`, `retractRemoved` or `retractAbsentRows` call or of one removal. The store keeps or loses such a record whole, and a write it refuses has written nothing: a refused write-down leaves the manager in legacy mode, a refused `presentRows` enters no row and tells the strategy nothing, and a refused `retractRows` takes nothing out. After any throw the window index is read again from the store. A write of one row is one record, through the single form, as on a chronicle without the batched append, where every row presented, and every row of the write-down, is a record of its own. The first batched record moves the store to chronicle's `MANIFEST` version 2 (see Breaking). A batch is one presentation point: a cut at any row it presented keeps the whole batch (see the `branchAt` entry). `bench/window/write-down-bench.mjs` measures the write-down both ways and checks they leave the same window; in two runs on one synthetic store of 50,000 rows on one machine (an Apple M5), the write-down took 64 to 87 ms in one record against about 3.9 s in 50,001, the log grew by 1.9 MB against 15.3 MB, and a reopen that reads the window took up to 0.3 s longer than one before the write-down against about 0.6 s longer. These are one store's numbers, not a guarantee for a resident store.
  - A branch starts with the window as it stood at its branch point: `fork()` and `branchAt()` carry it, and `derive()` lists it among the states the manager owns, whatever the strategy's derivation manifest names. A manager derived at the head starts with its parent's window and its arrived-and-not-presented rows, from the parent's reading of the window rather than a new read of the store. One derived from `atSequence` starts with the window as it stood then, which names only rows stored by then. `reopenDerived()` finds the window on the derived branch. A parent that hadn't presented a row by the branch point has no window written there, and the branch is in legacy mode.
  - A row removed with `removeMessage` or `removeMessages` leaves the window as `retractRows` takes a row out: a tombstone at its ordinal, so no other row's ordinal moves. In legacy mode nothing is written. A removal through another manager on the same slot isn't heard: a host takes that row out of each other window that holds it with `retractRemoved(ids)`, naming the rows the removal took, or with `retractAbsentRows()`, which finds every such row, at boot say (see the entry for them); each tells that manager's strategy, which lets go of what it folded of the row. `retractRows` takes a row the store no longer holds out by its id too, and also takes out a row the record still holds, which those two pass over. A tombstone that can't be written, or a window that can't be read before a range is removed, is logged, and the removal stands. Until one of those calls takes such a row out, it keeps its ordinal: the window's listing and the compile leave it out, but `ordinalOf` still gives its ordinal and a strategy's `StrategyContext.window.ordinals()` still maps it, so a host that keeps watermarks by ordinal takes it out of each window that holds it.
- `MessageStoreView.positionOf(id)`, optional: a message's position in `getAll()`. Compile provenance finds a raw body by its position instead of its sequence, since a window needn't be in sequence order; a run of raw entries still costs one lookup and reads no stored message (#273).
