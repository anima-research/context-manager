- A message cut at `maxMessageTokens` now says that later text was left out. The first text block past the cap that holds anything, text or an opaque item such as a Responses carrier, becomes one `[content omitted: this message reached its token limit]` block, in the autobiographical and windowed-passthrough strategies alike, where those blocks used to be dropped without a trace, so a message read as ending at the cut. A text block that holds nothing, empty or only whitespace, is left out across the cap as it already was past it, with no marker, where one crossing the cap used to be cut and given a truncation suffix; the cap ends there, as at a cut. A message whose every block is such a text block now carries the omission block alone when the cap leaves one of them out, where its whitespace was cut and given the suffix. Leaving one out no longer makes the summary it belongs to partial in the combined recall answer's layout, unless it gives up an item that a kept reasoning part pairs with: that part then goes out without its raw form, as after a cut, and the summary is listed partial. A summary the cap took something from that held anything, of which only text blocks that hold nothing reached the answer, is no longer listed in the combined recall answer's layout, with `recallEnvelope: 'xml'` or without, where it was listed partial: it shows the resident none of its history. A tool result whose content is a string already carried its own marker past the cap; an empty one now stays as it is, since it loses nothing. In the legacy combined recall answer (`positionedRecallPairs: false`), the marker goes where the first dropped block that held anything was, as in any message; with `recallEnvelope: 'xml'`, which spends the cap summary by summary, it goes once after the last answer when the cap leaves out a summary that holds anything, unless that answer's own cut already wrote it inside its envelope. That answer ends where the cap ended, even where the blocks the cap left out spent none of it, and a summary isn't admitted where the cap reaches it and leaves nothing of it that holds anything. An answer the cap admits no summary to is the omission block alone. A message the cap cuts nothing from, though its estimate passed the cap, comes back as it was and is no longer treated as cut: the xml combined answer lists such a summary as shown whole, where it listed it as partial. A capped message is still priced at `min(estimate, cap + 50)`. In the windowed-passthrough strategy, a message the cap looks at but cuts nothing from is now priced at its full estimate, as it renders, where it was priced at `min(estimate, cap + 50)`. The two differ only when such a message's estimate passes `cap + 50`, as one with a large tool call can, and the window's total then rises by the difference. That price isn't a bound on what a capped message renders: blocks the cap doesn't read, such as a tool call or thinking, go out whole, the cut's suffix and a string result's omission notice could already take it past, and the marker, 14 estimated tokens, adds to them. The combined recall answer is priced as rendered, so a capped one now costs the marker's tokens more. The first compile after upgrading changes the bytes of every message the cap drops text from or leaves a text block that holds nothing out of, and misses the prompt cache from the first such message on. In the windowed-passthrough strategy, the new price can also move the window's start, which changes the prompt from there on too.
