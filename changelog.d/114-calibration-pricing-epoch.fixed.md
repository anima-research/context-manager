- The persisted estimator-calibration multiplier is stamped with the token-pricing epoch it was learned under (`AutobiographicalStrategy.CALIBRATION_PRICING_EPOCH`), and a multiplier from another epoch is discarded on load (start from 1.0). A store that had pinned 1.8 under the flat-600 signed-thinking price otherwise reopened estimating ~1.8× its real size. When that plan exceeded the hard budget, the first compile threw `OverBudgetError` before any inference, so no sample could ever decay the multiplier: a permanent startup crash loop.
- The discard is persisted (`{multiplier: 1, pricing: <current epoch>}`) for records from an older or unstamped epoch, so rolling back to a binary that ignores the stamp can't reload the stale multiplier. A record from a newer epoch is left on disk untouched (a later binary owns it) and is simply not used.
- A discard is no longer only one log line. It is a `console.warn` naming the size of the change and how to re-stamp the old value. It is also recorded as `reset: {discardedMultiplier, fromEpoch, at}` in the persisted calibration state, and exposed with the multiplier and epoch as `RenderStats.calibration` (so hosts that surface render stats, such as connectome-host's `/healthz` `contextComposition`, show it). The record survives restarts and later learning; an operator re-stamp without it clears it.
- **Operators:** every store that has run 0.11.0 holds an unstamped multiplier, and the first open after upgrading resets it to 1.0. That is right for a multiplier learned against the old flat thinking price, but wrong for one that is still accurate, for example one that mostly corrects for a non-Anthropic tokenizer: the window refolds by the old multiplier's ratio and creeps back over many turns, re-busting the cache. Before upgrading such a store, check its multiplier against provider-billed input tokens. If it holds, re-stamp it with the host stopped: `setStateJson('<ns>/autobio:calibration', { multiplier, at, pricing: 1 })`.
