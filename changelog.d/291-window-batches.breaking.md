- **Host operators (stores a host that presents writes):** the window index writes a write-down, the rows of one `presentRows` call and the tombstones of one call as one batched record, through chronicle's identity-stamped batched append, `appendManyToStateJsonWithIdentity` (see the window index entry and the chronicle entry), and the first such record moves the store's chronicle `MANIFEST` from format version 1 to version 2. Chronicle releases from before batched appends, 0.5.0 and earlier, refuse a version 2 store at open, with "Unsupported store version: 2". So once a host that presents has written down a window with a row in it, or presented two rows in one call, the store no longer opens on an older chronicle, nor under a context-manager or host whose chronicle range resolves one, such as context-manager 0.24.0 (`^0.5.0`).
  **Who needs to act:** a host that calls `presentRows` or `retractRows` (agent-framework's presentation index, #291) and may roll back its chronicle or context-manager afterwards.
  **Migration:** none going forward. Going back, there is none for a store that holds a batch: keep a copy of each store from before its first presenting boot on these versions if a rollback must stay possible.
  **Unchanged:** a manager that never presents is in legacy mode and writes nothing to the window index, so a host that doesn't present keeps its version 1 store. A window all of whose writes are single rows (an empty record's write-down, which is its header alone, then one row per call) is written one record each, as before, and keeps version 1 too. A window index a pre-release build wrote one record per row reads as one written in batches.
