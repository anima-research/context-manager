- Fold receipts follow a window a host presents (agent-framework #291). Once rows are presented on a branch (`presentRows`), a compile's rendered layout counts its members by window-index ordinal instead of store sequence, so a compile whose window was presented out of record order is accepted; `acceptRound` refused it before. `RenderedLayout` is now `v: 3`: `keyedBy` says what `members` count (`'sequence'` while the window is the record, `'ordinal'` once rows are presented), and `memberSequences`, parallel to `members`, gives each member's store sequence, which receipts still name a message by (`FoldSpanBound.sequence`). The receipt format doesn't change.
  - `RenderedLayout`'s type changes with it, in legacy mode too: every compile's `provenance.layout` is `v: 3` with `keyedBy` and `memberSequences`, where it was `v: 2` without them, though the messages compiled are the same. TypeScript code that builds a layout by hand, such as a test double, sets both and `v: 3`; a `v: 2` literal no longer type-checks. `acceptRound` still takes a layout without `keyedBy`, such as a provenance an earlier release's compile returned and a host carried across the upgrade: it reads its members as store sequences, as they were, and records it in format 3. A `keyedBy` it doesn't know is refused.
  - Once rows are presented, a receipt's run (`FoldChange`, a baseline's `FoldLayoutRun`) is consecutive in the window's order, not the record's: `first` and `last` name its first and last messages, and the run can hold a message stored after `last` or before `first`, presented between them, and `first.sequence` can exceed `last.sequence`. A reader that turns a run into the record's rows by sequence range reads a window's run wrongly: read the run's messages from the window.
  - The fold journal records a layout keyed by ordinal as accepted-layout format 4, and one keyed by sequence as format 3, as before, so a host that never presents writes what it wrote. A layout's members are never compared with those of a record of the other format: an acceptance whose layout's format differs from that of the branch's newest record writes a baseline there, and a warning says so (once per record). That is the first acceptance on a branch of a compile made after its first presentation, and again any acceptance that switches back, such as one of a compile made before the first presentation accepted after one made after it. Receipts are listed across both formats: that baseline links to the branch's receipts before it.
  - A compile is recorded by what its layout counts, not by the window when it is accepted: one made before the first presentation and accepted after it is format 3, compared with the layout before it.
  - Rollback, of a store a release before this one can still open (one at chronicle `MANIFEST` version 1, which holds no batched window write; one at version 2 doesn't open there at all, see the window batches entry): such a release reads a format-4 record as one of another format. While a branch's newest record is format 4, it lists none of that branch's receipts, the format-3 ones before the presentation included. Its first acceptance there writes a baseline that links to no receipt before it, so the branch's receipt history starts again from that baseline: every later release, this one included, lists only receipts from that point on, and the receipts before it stay in the record but aren't listed on that branch again, with no note to say so.
