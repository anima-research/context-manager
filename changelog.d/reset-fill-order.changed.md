- After a head-window reset (`ContextManager.resetHeadWindow()`), a compile sends what happened in the order it happened while the new head fills: the history before the reset, then the `[Topic Transition]` message and each message since, so the newest message is the last one sent. Once a message no longer fits `headWindowTokens`, the head goes first, as before: the transition and the new topic's opening, then the history, then the rest. Before, the head went first from the reset on, so while it filled the newest messages came before the old history and the request ended on the old topic.
  - **Whole messages in a reset head.** With a head window (`headWindowTokens` above 0) and history before the reset, the transition is always whole in the head, whatever its size. After it, the head takes whole messages (one split into shards as it was stored counts as one) while they fit, and ends before the first that doesn't, or before the one ahead of it when that one holds a tool call, so a call stays with its result. As before, the ratchet guard (#122) can then extend the head over messages compression never took, now leaving out pinned messages at its end after the last pinned tool result, which compression doesn't take. So a message whose first part was kept out of compression while its rest was compressed still stays in two parts when that part isn't pinned, so it isn't compressed out of order, or when that part holds a tool result, and a call the guard keeps in the head can be sent apart from its compressed result, as before. Before, a transition bigger than the window left the hierarchical select's head empty, so the transition itself came after the history, and the adaptive selects ended the head inside a long transition or first message and sent its rest after the history. So a transition bigger than what the budget leaves beside the rest is refused as a head is, where the adaptive selects could send it with its later part folded. A compression or merge request for history from an earlier topic gets that topic's head by the same rule, since a past head ends by the walk the live head takes (#317). Without a reset the head still ends where its tokens run out, and the ratchet guard extends it as before.
  - **Prompt cache.** Before, the reset's compile rewrote the whole request after the system prompt, and each compile in which the head grew rewrote the history again. Now the reset's compile sends the history's messages as before with the transition after them, unless an earlier reset's head went first in that request, which the reset then puts back in store order, rewriting the request once. Compiles while the head fills add to the end, and the compile where the head goes first rewrites the request once; each compile decides that from the head window's end as it prices it, so a calibration change right at that point can send store order once more. Under membrane's XML formatter, which joins the text between cache markers, a marker that moves at the reset's compile, as the hierarchical select's does from the old head's end to the history's, changes the request from there. A fold of the history while the head fills rewrites the request from that fold on, where before the fill's own rewrite took it in. The usual one is the old head's: the reset makes it compressible, and it sits at the history's front.
  - `renderAsNewest` gives a filling reset head's messages as the compile sends them, last. Before, it gave null for them. Render stats and over-budget refusals still count a filling head as the head, and every select still budgets the history beside it as when the head goes first.
  - A store whose reset head is filling, or ends inside a message, can change its head and order at its first compile after the upgrade, which rewrites its request once. Where the new head's end leaves messages that were never chunked before chunks that follow them, the ratchet guard keeps them in the head (#122), which can leave a message in two parts until the next reset, unless they're pinned messages at the head's end after the last pinned tool result. Its transition goes whole into the head either way.
