- After a head-window reset (`ContextManager.resetHeadWindow()`), a compile sends what happened in the order it happened while the new head fills: the history before the reset, with its system changes in their places, then the `[Topic Transition]` message and each message since, so the newest message is the last one sent. Once a message no longer fits `headWindowTokens`, the head goes first, as before, and takes the system changes stored before it. Before, the head went first from the reset on, so while it filled the newest messages came before the old history and the request ended on the old topic. `renderAsNewest` gives a filling head's messages as the compile sends them, last, where it gave null.
  - **Whole messages in a reset head.** With a head window (`headWindowTokens` above 0), the transition is always whole in it, whatever its size. After it, the head takes whole messages (one split into shards as it was stored counts as one) while they fit, and ends before the first that doesn't, or before the one ahead of it when that one holds a tool call, so a call stays with its result. As before, the ratchet guard (#122) can then extend the head over messages compression never took, which can end it inside a message, as without a reset. A transition bigger than what the budget leaves beside the rest is now refused, as a head is, where the adaptive selects could send it with its later part folded.
  - **Past heads.** A compression or merge request for history from an earlier topic gets that topic's head by the same rule, since a past head ends by the walk the live head takes (#317).
  - **Prompt cache.** The reset's compile keeps the history where the request had it, unless an earlier reset's head went first there, and adds the transition after it. Each compile while the head fills adds to the end of the request, and the compile where the head goes first rewrites it once. Under membrane's XML formatter, which joins the text between cache markers, a marker that moves at the reset's compile changes the request from there. Before, the reset's compile rewrote the whole request after the system prompt, and each compile in which the head grew rewrote the history again. A fold of the history while the head fills rewrites the request from that fold on. A store whose reset head is filling, or ends inside a message, can change its head and order at its first compile after the upgrade, which rewrites its request once.
