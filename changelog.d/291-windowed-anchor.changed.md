- `WindowedPassthroughStrategy`'s anchor follows the agent's window (agent-framework #291). While the window is the record (legacy mode) the anchor is a sequence, and its slot holds `{ anchor }`, as before. Once a host presents rows on a branch (`presentRows`), the anchor is an index ordinal: the window is the row at it and every row presented after it, in window order. An ordinal counts the window before the view filter and never moves, so neither the filter nor a row taken out with `retractRows` shifts the anchor.
  - A sequence anchor, from an earlier release or set before the first presentation, is converted when its branch is first read in presented mode, to the ordinal of the first row in the window stored at that sequence or after. The index is first written down in record order, so the window at the conversion is the one the sequence gave, and the messages compiled stay byte for byte the same. Each branch's slot is converted where it is read, and the conversion is written to it then, as `{ anchor, ordinal, v: 2 }`, by the compile, `renderAsNewest` or `getAnchorOrdinal()` that made it; a preview (`dryRun`) converts for itself and writes nothing, and an anchor of 0, the start, is never written, since it converts to the whole window whenever it is converted. Converting the same sequence again later could give another ordinal, and so another window with no move, once a row stored before it has been presented after the row it names (taken out and presented again, as an undo and its redo do), so a reload reads the ordinal the window was sent from. The conversion is exact until such a row is presented: a host that presents at boot converts at its first compile.
  - `setAnchor(sequence)` converts the same way, at the call, or to the ordinal the next presented row will take when no row in the window is stored at the sequence or after. So a tune-out's start given as `currentSequence()` keeps every row presented to the agent from then on: a row stored before the anchor's sequence and presented later is in the window, where a sequence anchor left it out. The sequence the anchor already has changes nothing, so setting a tune-out's start again at a restart keeps the window, but only while the anchor hasn't moved since. A re-anchor on overflow gives the anchor the sequence of the row it starts the window at, so a tune-out's start set again after one, at a restart or when another tune-out starts, is converted again, against the window as it stands, and once rows have been presented out of record order that can leave out a row the first conversion's window held. A host that sets a place again keeps it by ordinal: record `indexLength()` at the tune-out's start and give it to `setAnchorOrdinal`.
  - New: `setAnchorOrdinal(ordinal)`, which throws in legacy mode and for an ordinal outside the index, and `getAnchorOrdinal()`. `getAnchor()` still gives a sequence: the one `setAnchor` was given, or that of the row a re-anchor started the window at. A persisted ordinal past the branch's index length resets to 0 with a warning, as a sequence past the branch head does.
  - `StrategyContext.window` (optional, type `WindowIndexView`): the manager's window index as a strategy reads it, with `mode()`, `ordinals()`, `length()`, `ordinalFrom(sequence)` and `sequenceFrom(ordinal)`. A context built without one reads as legacy mode.
  - Rollback: the slot's `anchor` stays a sequence at or before the branch head, so a release before this one loads it and starts its window there, by sequence.
