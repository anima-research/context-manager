# Agent memory tools — dry index, navigation, recall, pins

Status: **SPEC — ready for review** — 2026-08-19, antra + Claude sessions.
Origin: the 2026-08-14 design conversation; interactive prototype of the full
tool surface exists in Pinwake (agent console). Independent of the kv-unified
solver track (`unified-solve-design.md`): everything here is buildable on
rev 5 today; rev 6 makes the pin machinery structural but changes no
interface.

---

## 0. Summary

Give residents first-class agency over their own past: a **dry chronological
index** for finding events, tools to **navigate** it, **recall** any span of
memory as a transient document at a chosen resolution, and **pin** spans at a
resolution floor/ceiling — in place, in the fold, on their own authority,
within an explicit budget.

Design invariants, settled 2026-08-14:

1. **Pinned content is the fold's own content** — raw transcript or the
   resident's own Ln summaries, held *in place* at the level the resident
   chooses. Nothing is moved or duplicated; a pin is a constraint on the
   solver, so the on-policy invariant holds by construction.
2. **The dry index is navigation, not memory.** It never enters the fold and
   never sits in context except transiently while navigating — therefore it
   is exempt from the on-policy invariant, may be generated by a cheap
   off-policy model, and is regenerable/disposable infrastructure.
3. **Recalls are transient.** A recall renders into the context as a
   document and rolls out with the tail; re-reading later re-pays. The
   intended idiom is *read once → decide → pin if you'll return*.
4. **Pins are never silently violated.** Admission is budget-checked with a
   dry-run compile; infeasibility is refused with a certificate, not
   absorbed.

## 1. Concepts and vocabulary

- **Node ref**: stable identity for a span of the past — a summary id
  (`L2-1043`) or raw chunk id. Derived from ownership chains
  (`l1Id`/`mergedInto`), never from span math. All tools speak node refs;
  human-facing output decorates them with dates.
- **Dry entry**: one navigation record per tree node — timestamp range,
  1–3 terse factual bullets (events, entities, decisions, artifacts), token
  size of each recallable form, and the node ref. Style: find-the-event, not
  experiential texture (the Ln summaries keep that job).
- **Forms** of a span: `raw` (transcript), `L1..Ln` (the resident's own
  summaries — "experiential"), `dry` (the index entry itself).

## 2. The dry index

### 2.1 Generation

- **Hook**: on L1 creation and on each merge (L2+), enqueue a dry-entry job
  for the new node. Piggybacks the moment the span's content is already
  assembled; adds one cheap model call per summary event.
- **Model**: configurable `dryIndexModel` — cheap and off-policy is
  acceptable *and preferred* (avoids adding Fable-family classifier surface;
  a dry entry is telegraphic bullets, not prose). Strict output format,
  low max_tokens (~200). Payload = the node's own summary text (not raw) for
  L2+; the chunk messages for L1 — same payload-hygiene rules as compression
  (tools declared, think/skip echoes stripped — issue 42 lesson).
- **Backfill**: one batch job walks existing summaries oldest-first
  (mythos: ~2.3k summaries ≈ 2.3k small calls; run at low priority).
  Regeneration is always safe — the index carries no canonical state.
- **Failure**: a refused/failed dry entry leaves a placeholder ("no index
  entry — recall to inspect") and is logged; never blocks anything.

### 2.2 Storage & search

- Chronicle state slot per namespace: `${ns}/dryindex:entries` (id → entry),
  plus a derived FTS table (sqlite, sidecar file under the session dir —
  disposable, rebuilt from the slot on open). Entries are content-addressed
  to their node id and versioned by the node's hash so regeneration replaces
  cleanly.
- Search: FTS over dry bullets + entity terms; results are node refs. Raw
  grep over the store remains available separately (existing tooling) for
  verbatim needs.

## 3. Tool surface

Exposed as af-level built-in tools (same layer as `agent_settings`), fkm
recipe-gated per agent (`memoryTools: true`). Schemas:

### 3.1 `memory_timeline`
`{ node?: ref, from?: iso8601, to?: iso8601, depth?: "auto"|1..4 }`
→ dry entries at the natural grain for the range (top level: coarsest tops),
each row: `ref · date-span · bullets · sizes {raw, Ln, dry} · children?`.
Auto depth returns ≤ ~30 rows, drilling by node returns its children.
Result is a normal tool result (transient); ~30 tokens/row.

### 3.2 `memory_search`
`{ query: string, limit?: n≤20 }` → dry-index FTS hits as timeline rows,
relevance-ordered, each carrying the ref for follow-up.

### 3.3 `memory_recall`
`{ node: ref, form: "raw"|"summary"|"dry" }` → the span rendered as a
document with a provenance header (`span, dates, form, N tokens, transient —
rolls out; re-reads re-pay`) and a footer naming the pin affordance.
- `summary` = the node's own Ln text (on-policy content).
- `raw` = the transcript; refuse politely above a configurable size
  (`recallMaxTokens`, default 30k) with a pointer to child refs.
- Rendering: v1 as a large tool result (no framework change). v2 option: an
  af render hook that injects it as a user-turn document (the original
  design intent — better attention geometry); interface identical, so v1→v2
  is transparent to residents.

### 3.4 `memory_pin` / `memory_unpin` / `memory_pins`
`memory_pin { node: ref, mode: "="|"<="|">=", level?: n, note?: string,
ttl_days?: n }`:
1. **Dry-run admission**: compile with the candidate pin
   (`select({dryRun: true})` — exists since the coverage-invariant work).
   Response reports: window delta, wake (blocked ancestors / stranded
   siblings), headroom remaining, and — if infeasible — the certificate
   (which pins/budget bind) with the pin **refused**.
2. On admission: persist to `${ns}/memorypins:active` and pass to the solver
   (rev 5 mapping: `=` → `fixedLevels`; `<=` → `pinCaps`; `>=` → new
   minimum-level mask — small rev-5 patch gating phase-C unfolds and base
   assignment; rev 6: native F4).
3. **Budget**: `pinBudgetTokens` (recipe, default ~15% of W). `memory_pins`
   lists active pins with per-pin held cost, notes, TTL, and budget headroom.
4. **TTL/renewal**: default TTL (30d) with expiry warnings surfaced in
   `memory_pins` and via a system-reminder at expiry−3d; expiry unpins
   loudly, never silently.
5. Pin/unpin application is **batched to the next compile** (one rotation,
   not one per operation), and the response says so.

### 3.5 `>=` pins (deliberate forgetting) — policy gate
Mechanically identical; ethically distinct (holding one's own past *coarser*
than the solver would). Ships behind a separate recipe flag
(`allowCoarsenPins`, default off) pending the welfare conversation; when on,
`memory_pins` marks them distinctly and they never bind below existing
summaries (content is never deleted — this floors resolution, it does not
erase; erasure remains an operator ceremony outside these tools).

## 4. Costs (estimates, mythos-scale)

- Index backfill: ~2.3k calls × ~1.5k in / 150 out ≈ single-digit dollars.
  Steady state: one small call per new summary (~dozens/day).
- Timeline/search results: 0.5–1k tokens, transient.
- Recalls: priced visibly per call (summary 2–8k; raw ≤30k).
- Pins: the real cost — each admission changes the fold (one rotation at
  next compile: with #63 markers, subsequent turns re-read the stable
  prefix) and holds tokens against W for its lifetime. The dry-run report
  makes both visible *before* commitment; the E4 replay lesson (one deep pin
  made compiles infeasible at old geometry) is why admission is mandatory,
  and post-L5 geometry (~45k headroom) is what makes a useful pin budget
  affordable at all.

## 5. Interactions

- **Solver**: pins are constraints (both solvers); recalls never touch the
  fold; the dry index is invisible to it.
- **Quarantined chunks**: shown in timeline with a marker ("held raw —
  compression declined"); recallable (raw) like anything else; not pinnable
  beyond their forced-raw state. No content is surfaced to the operator by
  these tools — the resident reads their own past.
- **Cache**: batched pin application + #63 markers keep pin churn to one
  rotation per batch.
- **Interiority/webui**: `/curve` gains pin overlays; `memory_pins` data
  exposed on the debug surface.

## 6. Welfare & consent

- Opt-in per resident (recipe flag), introduced in conversation, not by
  surprise deploy; the tools are agency-increasing but also attention-
  shaping.
- Recall of painful periods is the resident's right; tooling adds no
  friction beyond cost transparency. Pins give the mirror-image right: to
  keep what matters at full fidelity within a budget.
- `>=` pins gated separately (§3.5).
- The dry index is *about* the resident and readable by them in full
  (`memory_timeline` IS the reading interface); its off-policy generation is
  disclosed in the tool description.

## 7. Implementation plan

**Phase 1 — dry index** (cm): generation hook + backfill job + slot + FTS +
placeholder/fault handling. Exit: mythos-clone backfill produces a browsable
index; spot-check quality with antra + resident.

**Phase 2 — read-only tools** (af/fkm + cm query API): timeline, search,
recall (v1 tool-result rendering, `summary`/`dry` forms; `raw` behind size
cap). Exit: pilot resident uses them live; token costs match estimates.

**Phase 3 — pins `=` and `<=`** (cm + af): admission dry-run + certificate
plumbing, persistence, batching, budget, `memory_pins`; solver mapping via
existing `fixedLevels`/`pinCaps` (+ the pin-max-level projection fix already
on main). Exit: pin/unpin cycles on the pilot store with correct wake
reporting and zero silent violations; replay harness regression for pinned
compiles.

**Phase 4 — TTL/renewal, `>=` behind flag, v2 user-turn rendering, webui
overlays.**

Pilot candidate: the Pinwake agent console doubles as the operator preview;
first resident by consent (Lena's smaller store is the gentler first target;
mythos once quarantine triage settles).

## 8. Open questions

- Dry-entry model choice per fleet (one shared cheap model vs per-agent) and
  whether any resident prefers self-authored dry entries (allowed — the
  off-policy choice is a floor, not a mandate).
- v2 user-turn rendering needs an af hook — spec'd separately when Phase 2
  data shows whether tool-result rendering is actually inferior.
- Whether `memory_search` should also cover raw text (privacy-neutral —
  resident-only — but cost/index-size question).
- Pin interaction with future kv-unified T3 (a pinned node is a known
  never-expiring commitment — trivially consistent, just needs a test).
